

MAJOR COMPONENTS


1. MAIN ENTRY POINT (main.py)

Responsibility:
    Primary orchestrator and controller of the entire application
    Initializes all subsystems and manages the main event loop
    Maintains conversation state and recipe management state
    Handles user input processing pipeline

Key Responsibilities:
    Initialize Database connection
    Initialize AI Chat model
    Start Flask web API server for browser communication
    Manage conversation lifecycle (greeting, listening, processing)
    Coordinate between AI, database, TTS, and UI

Interfaces:
    Imports: ai_utils, db_query_handler, recipe_manager, tts, stt, camera, interface
    Functions called: listen(), play(), start_flask_app(), execute_query()
  
Data Flow:
    Receives user speech from listen() → stt module
    Sends prompts to AI Chat system → ai_utils.Chat
    Gets recipe data from database → db_query_handler
    Sends synthesized speech to play() → tts module
    Displays UI through interface.ChefBonoUI
    Captures images through camera.get_frame()

Communication Pattern:
    SEQUENTIAL: User input → STT → AI processing → Database query → TTS playback
    Maintains state: latest_query_result, recipe, chat history


2. AI LOGIC MODULE (ai_logic/ai_utils.py)

Responsibility:
    Manages conversational AI through Google Gemini API
    Maintains chat history and context windows
    Processes natural language prompts
    Generates contextual responses for recipe queries

Key Classes:
    Chat: Manages conversation state and API calls
        input_token_limit: Maximum input tokens
        output_token_limit: Maximum output tokens
        context_window_limit: Conversation memory limit
        chat_history: Stores user-assistant message pairs
  
    AIUtils: High-level AI interface
        language: Language setting (english/turkish)
        Manages multiple chat instances
        Integrates with database queries

Key Methods:
    Chat._update_chat_history(): Records messages in conversation
    Chat._pop_convo(): Removes last exchange for memory management
    Chat._is_list_of_parts(): Validates Google API Part objects

Interfaces:
    External API: Google Gemini API via google.genai
    Database Integration: Uses db_query_handler for recipe context
    Uses sqlite_vec for vector embeddings

Data Structure:
    chat_history: List of tuples (role: "user"/"assistant", content: List[Part])
    Stores message history as Google API Part objects for multimodal support

Communication Pattern:
    Bidirectional with main.py: Receives prompts, returns AI responses
    Queries database for recipe embeddings
    Maintains context across multiple turns


3. DATABASE LAYER (database_utils/db_query_handler.py)

Responsibility:
    Handles all SQLite database operations
    Manages recipe queries with vector embeddings
    Serializes/deserializes binary data (embeddings)
    Provides interface for recipe search and retrieval

Key Class:
    Database:
        db_path: Path to SQLite database file
        Manages connections with sqlite_vec extension for vector search

Key Methods:
    execute_query(query, params): Execute SQL with parameters
    get_recipe(recipe_name): Retrieve specific recipe
    deserialize_embedding(): Convert binary embedding to float list
    serialize_bytes(): Handle binary data encoding/decoding

Database Tables (from database_structure.sql):
    recipes: Core recipe data with attributes
        id, name, ingredients, preparation
        meal_type (Breakfast/Lunch/Dinner)
        main_ingredient, nationality
        Dietary flags: vegetarian, vegan, gluten_free, dairy_free, nut_free
        Diet goals: high_fiber, weight_loss_diet, muscle_gain_bulking, balanced_healthy
        Nutrition scores: carb, protein, fat, calorie, sugar, spice_level, preparation
    recipes_vec: Vector embeddings for semantic search

Data Flow:
    Receives SQL queries from main.py → ai_utils.py
    Connects to recipes.db with sqlite_vec extension
    Returns recipe dictionaries with deserialized embeddings

Communication Pattern:
    Called by: main.py, ai_utils.py
    Returns: List of recipe dictionaries
    Thread-safe with sqlite3 connection management


4. RECIPE MANAGEMENT (recipe/recipe_manager.py)

Responsibility:
  - Define data model for recipes
  - Store recipe attributes and metadata
  - Support filtering and categorization

Key Class:
    Recipe:
        Core fields: id, name, ingredients, preparation, meal_type
        Attributes: main_ingredient, nationality
        Dietary flags: vegetarian, vegan, gluten_free, dairy_free, nut_free, high_fiber
        Diet categories: weight_loss_diet, muscle_gain_bulking, balanced_healthy
        Nutrition scores: carb, protein, fat, calorie, sugar, spice_level (0-1 scale)
        Difficulty: preparation_time_score, preparation_difficulty_score
        meal_class: Classification for UI display

Interfaces:
    Used by: main.py, database_utils modules
    Consumed by: AI for filtering and recommendations

Data Structure:
    All scores normalized to 0-1 range for consistent filtering
    Supports complex queries based on multiple criteria

Communication Pattern:
    Passive data model; used for deserialization from database
    Provides standardized recipe representation across system


5. BUILDING PHASE / DATA PIPELINE (building_phase/)

Responsibility:
    Scrape recipes from external sources
    Process and enrich raw recipe data with AI
    Generate vector embeddings for semantic search
    Populate database with processed recipes

Components:

    a) scrap_recipes.py (Web Scraper)
        get_with_retries(): Robust HTTP requests with retry logic
        _scrap_html(): Parse HTML and extract recipe components
        Handles: recipe name, ingredients, preparation steps
        Error handling for network issues and missing data

    b) row_adder.py (Data Processing & Enrichment)
        serialize_f32(): Convert embeddings to binary format
        get_last_processed_line(): Resume interrupted processing
        Thread pool processing for concurrent recipe enrichment
        Thread-safe database writes with Lock
        Progress tracking in database_utils/progress.txt


Data Sources:
    building_phase/scraped_recipes.jsonl: Raw scraped recipes
    building_phase/our_recipes.jsonl: Manually created or verified recipes

Interfaces:
    Input: External recipe websites
    Output: database_utils/recipes.db (populated)
    Uses: ai_utils for embeddings and enrichment
    Uses: sqlite_vec for vector storage

Data Flow:
    1. Scrape HTML from websites
    2. Extract recipe components
    3. Enrich with AI (embeddings, categorization)
    4. Serialize embeddings
    5. Store in SQLite with vector table
    6. Track progress for resumable processing

Communication Pattern:
    Standalone batch processing
    Called once during setup, not during runtime
    Thread pool for performance


6. TEXT-TO-SPEECH (tts_and_stt/tts.py)

Responsibility:
    Synthesize text into speech using Piper TTS
    Distribute audio to web browser via web_api_app
    Support multiple languages

Key Functions:
    play(text, model_path, language): Main TTS entry point
        Uses Piper voice models (pre-trained ONNX files)
        Supports: English (female voice), Turkish
        Generates WAV audio to temporary file
        Sends base64-encoded audio to web API

Models Used:
    en_US-hfc_female-medium: English female voice (ONNX format)
    tr_TR-dfki-medium: Turkish voice (ONNX format)

Interfaces:
    Called by: main.py
    Sends audio to: tts_and_stt/web_api_app.py (HTTP POST)
    Manages: Playback process threading

Architecture:
    Non-blocking playback (background thread)
    Uses Piper Voice library for synthesis
    Temporary WAV file generation
    HTTP-based browser distribution
    Flag management: bono_started_speaking, bono_stopped_speaking

Communication Pattern:
    Receives text from main.py
    HTTP POST to web_api_app.py with base64 WAV data
    Browser receives audio via WebSocket (handled by web_api_app)


7. SPEECH-TO-TEXT (tts_and_stt/stt.py)

Responsibility:
    Capture user speech and convert to text
    Manage browser-based speech recognition
    Control listening state and timeouts

Key Functions:
    listen(greeting, language): Main STT entry point
        Calls start_listening_browser_remote()
        Polls get_latest_transcript() for results
        Waits for speech completion or timeout
        Returns recognized text string
  
    get_speech(): Low-level speech capture loop
        Continuous polling for speech segments
        Handles prefix removal ("yes" filter)
        Timeout and silence detection
  
    start_listening_browser_remote(): Trigger browser recording
        HTTP POST to web_api_app.py
  
    stop_listening_browser_remote(): Stop browser recording
        HTTP POST to web_api_app.py

Interfaces:
    Called by: main.py
    Gets transcripts from: tts_and_stt/web_api_app.py (HTTP)
    Uses: Kaldi speech recognition (in stt_model/ directory)

Speech Models:
    stt_model/: Kaldi acoustic models
        am/: Acoustic model (final.mdl)
        graph/: Language model FSTs
        ivector/: Speaker adaptation models
        conf/: MFCC and model configuration

Communication Pattern:
    Listens for HTTP responses from web_api_app
    Polls transcript file at intervals
    Blocks until speech recognized or timeout occurs


8. WEB API SERVER (tts_and_stt/web_api_app.py)

Responsibility:
    Bridge between desktop app and web browser
    Manage SocketIO connections for real-time communication
    Handle TTS audio distribution to browser
    Manage STT transcription relay

Key Endpoints:
    /control/start_listening: Trigger browser STT
    /control/stop_listening: Stop browser STT
    /tts: Send audio to browser
    SocketIO events: emission of speech, control signals

State Management:
    _CURRENT_TTS_ID: Track active TTS playback
    CONNECTED_FLAG_FILE: Detect browser connection
    TRANSCRIPT_FILE: Store latest speech recognition result

Data Flow:
    Browser connects via SocketIO
    Desktop app sends TTS audio via HTTP
    Browser plays audio, captures speech
    Browser sends transcriptions to server
    Server stores in /tmp/bono_latest_transcript
    Desktop app polls for transcripts

Communication Pattern:
    Bidirectional: Desktop ↔ Flask Server ↔ Browser
    HTTP for TTS and control commands
    SocketIO for real-time speech events
    File-based state for transcript storage


9. USER INTERFACE (UI/interface.py)

Responsibility:
    Provide visual interface for user interaction
    Display recipes and preparation steps
    Show conversation history
    Handle UI state management

Key Class:
    ChefBonoUI:
        Built with Tkinter (GUI framework)
        Color scheme: Professional orange/green palette
        Responsive layout (1150x720px, non-resizable)
        Multi-screen navigation

UI Components:
    Chat display area
    Recipe display section
    Step-by-step preparation guide
    Input controls
    Status indicators

Color Palette:
    Primary: Orange (#F4845F)
    Success: Green (#34C77B)
    Error: Red (#EF6461)
    Backgrounds: Warm off-white (#FFFAF5)

State Variables:
    current_recipe: Name of selected recipe
    current_step: Step number in preparation
    is_running: Execution state
    steps: List of preparation steps

Interfaces:
    Called by: main.py (but optional for CLI mode)
    Displays: Recipe data from database
    Shows: Chat conversation history
    Reflects: TTS/STT state

Communication Pattern:
    Observes: main.py conversation state
    Renders: Recipe and conversation display
    Can be bypassed for headless operation


10. CAMERA / VIDEO CAPTURE (recording_utils/camera.py)

Responsibility:
    Capture video frames from camera
    Save frames for visual context
    Handle platform-specific camera initialization

Key Functions:
    _open_camera(camera_index): Cross-platform camera initialization
        macOS: Prefer CAP_AVFOUNDATION backend
        Fallback: Generic video capture
  
    capture_every_second(output_file_path, camera_index, interval_sec, jpeg_quality):
        Continuous frame capture at specified interval
        Atomic writes (temp file + rename) to prevent corruption
        Configurable output format (JPEG/PNG)
        Automatic directory creation

Atomic Write Pattern:
    Write to: current_image.tmp.jpg
    Move to: current_image.jpg
    Prevents: Incomplete frame reads by other processes

Interfaces:
    Called by: main.py
    Output: recording_utils/current_image.jpg
    Uses: OpenCV (cv2) for video capture

Communication Pattern:
    One-directional: Camera → Image file
    Non-blocking background thread capture
    File-based communication to main process

DATA FLOW EXAMPLES

FLOW 1: USER RECIPE INQUIRY

1. User speaks: "Show me avocado recipes"
2. main.py → listen() [stt.py]
    Sends signal to web_api_app to start browser STT
    Polls /tmp/bono_latest_transcript
    Returns recognized text: "Show me avocado recipes"

3. main.py → Chat.send_prompt(text) [ai_utils.py]
    AI Chat processes: "Show me avocado recipes"
    AI generates database query: SELECT * FROM recipes WHERE main_ingredient = 'avocado'

4. main.py → database.execute_query() [db_query_handler.py]
    Executes query with vector search
    Returns: List of avocado recipe dictionaries

5. main.py → Chat._update_chat_history()
    Stores user message and AI response
    Maintains context for multi-turn conversation

6. main.py → play(response_text) [tts.py]
    Synthesizes: "Found 5 avocado recipes..."
    Sends WAV to web_api_app via HTTP POST
    web_api_app broadcasts to browser via SocketIO
    Browser plays audio

7. main.py → UI.display_recipes() [interface.py]
    Updates Tkinter window with recipe list

FLOW 2: INGREDIENT MODIFICATION REQUEST

1. User: "Can you omit the onions?"
2. main.py → listen() → "Can you omit the onions?"
3. main.py → Chat.send_prompt()
   • AI has context: previous recipe selected
   • Modifies ingredients list
   • Returns modified preparation

4. Database query may be skipped (in-memory modification)
5. play() → TTS → Browser audio
6. UI updates with modified ingredient list

COMMUNICATION PROTOCOLS
================================================================================

HTTP Endpoints (web_api_app.py):
    POST /control/start_listening → Start STT
    POST /control/stop_listening → Stop STT
    POST /tts → Send audio to browser
    GET /latest_transcript → Retrieve last recognized speech

SocketIO Events:
    'connect': Browser connected
    'speech': Transcribed speech received
    'audio': Audio playback control

File-Based Communication:
    /tmp/bono_browser_connected: Connection flag
    /tmp/bono_latest_transcript: STT result storage
    database_utils/progress.txt: Data pipeline progress

Database Queries:
    Vector similarity search using sqlite_vec
    SQL with embedding comparisons for semantic search
    Parameter-safe prepared statements
